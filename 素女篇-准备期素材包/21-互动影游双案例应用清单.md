# 互动影游双案例应用清单（阿飘 × 新婚旧梦）

> 目的：吸收 TapTap 制造研究所两篇官方案例的方法论，转化为《素女篇》可直接执行的规格。
> 案例①《我的甲方是阿飘：视频断点与互动故事图》——媒体工程层（断点契约、seek 确认、读档恢复、三类媒体故障）。
> 案例②《重生：新婚旧梦：章节系统与多玩法剧情》——内容架构层（章节段落、统一完成结果、共享状态、资源释放）。
> 两案例出自同一工作室（丫够燥），合起来覆盖《素女篇》S6（视频接入）与 S8（存档/读档）两大技术风险点。
> 生成日期：2026-08-19　|　状态：待 8/19 建项目后随《12》一起上传 TTM

## 0. 一页速览：素女篇吸收了什么

| 案例要点 | 素女篇落点 | 落地文档/会话 |
|----------|-----------|---------------|
| 段落 = 最小制作单位，流程控制与玩法分离 | 章回体拆成 ~25 个段落，段落表数据驱动 | 本文件 §2 + 《12》§4.1；S1 骨架期定 |
| 所有玩法通过统一完成结果回到剧情流 | 对话/采花/印证/终局统一返回 `{done,...}` | 本文件 §3 + 《12》§4.2 |
| 共享状态独立保存，不依赖场景对象 | PlayerData 补 `flags`（跨段落标记）+ `schemaVersion`（版本化） | 本文件 §4 + 《12》§4 |
| 存档 = 叙事状态 + 媒体位置 | 存档补 `mediaPos`（node/video/breakpoint/timeSec） | 本文件 §4；S8 |
| 断点是媒体剪辑与游戏状态之间的契约 | 13 段视频断点交互时间表 | 本文件 §5 + 设计总览 §6.1；S6 |
| "可播放"≠"已到目标时间" | 读档恢复三步状态机（就绪→seek 确认→移除遮罩） | 本文件 §6；S8 |
| 循环视频 vs 剧情视频不同恢复策略 | 桃花粒子/章节卡背景可销毁重建；S1~S9 存位置恢复 | 本文件 §6；S6 |
| 预加载 ≠ 首帧就绪 | 下载→解码器→纹理→首帧→音频源逐层确认 | 本文件 §6；S6 |
| 移动端资源释放是玩法的一部分 | 视频结束即释放、离场显式销毁、记录播放器数量 | 本文件 §6；S9 |
| 分层验收 + 可重复回归 | 段落可达性 / 读档不闪帧 / 前后台连续 / 播放器回落 | 本文件 §7 + 《04》打磨期 |

**不适用部分（明确不吸收）**：64 节点故事图规模、7 种互动玩法框架（密码/拖拽/对峙/审讯/微博/QTE）、广告返回链路（素女篇首发非商业化）——素女篇只有 4 类玩法（对话选择 / 探索拾取 / 记忆印证 / 终局行动），用统一完成契约接入即可，不建多玩法框架。

## 1. 内容图总览：素女篇 = 5 个章节块 × ~25 段

案例②的核心主张："先写章节图（段落、目标、分支、结局、每段的输入与输出），再实现最小闭环。"

素女篇按剧本结构拆为 5 个章节块（不是 9 章——体量 8~15 分钟，别过度设计）：

```
ch0 楔子·桃花谷口（木）
  P01 视频S1(开场) → P02 探索(谷口) → P03 对话(开场三选,不计信念)
  → P04 讲述+视频S2(第一回) → P05 讲述+视频S3(第二回) → P06 讲述+视频S4(第三回)
  → P07 对话(接任务:五朵桃花)
ch1 收集·朝阳之谷（正文）
  P11 探索采花×5（谷口/桃树下/望夫崖/井边/守桃老人屋，拾取触发素女独白+札记解锁）
  → 采齐 5 朵 → P12 对话(前往洛水阴山)
ch2 第四回·洛水阴，无面泪（水）
  P21 过渡(进入洛水阴山) → P22 视频S5(无面鬼初见) → P23 无面鬼互动三选(信念+1)
ch3 第五回·记忆印，六艺寻
  P31 引导对话 → P32~P36 记忆印证×5（视频S6-x + 解读三选 + 信念+1）
ch4 尾声·无涕桃，人面何处
  P41 返回朝阳之谷 → P42 献花前对话 → P43 终局抉择(献花/摘桃)
  → P44 结局判定 → P45 结局视频(S7/S8/S9) → P46 制作名单 → 标题
```

**节点类型**（借案例①的故事图思想，只取 5 种）：

| 节点类型 | 职责 | 素女篇实例 |
|----------|------|-----------|
| 视频节点 | 播放媒体 + 声明断点 | S1~S9 |
| 对话节点 | 台词 + 选项效果 + 下一步 | 守桃老人讲述、无面鬼互动 |
| 探索节点 | 场景漫游 + 交互目标 | 采花、走近守桃老人 |
| 选择/印证节点 | 选项 → 信念/线索变化 | 解读三选、终局两行动 |
| 结局判定节点 | 按门槛选结局 | 重逢/放手/传说 |

> 段落表是内容数据，运行时只做两件事：**当前在哪一段、完成后去哪一段**。换剧本只改数据，不重写运行时。

## 3. 统一完成契约（接口草案）

案例②："所有玩法都通过统一的完成结果回到剧情流程。流程层只接收完成结果，再决定下一段。"

```lua
-- 每个玩法模块（对话/采花/印证/终局）结束时返回统一结果
-- 流程控制器只认 done；其余字段按段落表约定读取，未知字段忽略
local result = {
  done        = true,           -- 必填：本段落是否完成
  beliefDelta = {},             -- 可选：{ reunion=1 } / { release=1 } / { legend=1 }
  unlocked    = {},             -- 可选：解锁条目 { "journal_01", "blossom_wood" }
  flag        = nil,            -- 可选：写入 flags 的跨段落标记（如 "fed_water"）
  next        = nil,            -- 可选：显式指定下一段；缺省用段落表 next
  timedOut    = false,          -- 可选：超时/失败标记（素女篇暂无用例，为限时玩法预留）
}
```

**铁律**：
1. 流程控制器（`flow.lua`）只做：读段落表 → 实例化段落 → 收完成结果 → 推进下一段。
2. 玩法模块只做：收集输入 → 反馈表现 → 返回完成结果。**不得直接跳段、不得直接改剧情推进状态。**
3. 信念/线索/标记写入共享状态层（PlayerData），场景对象不持有跨段落数据。
4. 新增玩法 = 新增一个段落类型模块 + 段落表加一行，流程控制器零改动。

## 4. 存档契约扩展（叙事状态 + 媒体位置 + 版本化）

案例①："一个可继续的存档要同时记录当前节点、视频、断点序号和精确时间。"
案例②："需要跨存档读取或重启后继续生效的状态纳入版本化序列化。"

```lua
PlayerData = {
  schemaVersion = 2,                -- ⬅️ 新增：存档结构版本；加载时校验，低版本走迁移/兜底
  belief = { reunion = 0, release = 0, legend = 0 },
  blossoms = { wood = false, fire = false, earth = false, metal = false, water = false },
  memories = {},                    -- 已解锁记忆片段
  journal = {},                     -- 旅人札记条目
  flags = {},                       -- ⬅️ 新增：跨段落临时标记（喂水/陪坐/唤名 → 终局回声；章节解锁位）
  ending = "",                      -- "reunion" / "release" / "legend"
  endingsSeen = {},                 -- 结局收集（标题 0/3）
  playCount = 0,                    -- 通关次数
  mediaPos = {                      -- ⬅️ 新增：媒体位置（读档/断点恢复契约）
    node       = "",                -- 当前段落 id（如 "P22"）
    video      = "",                -- 当前视频 id（如 "S5"）
    breakpoint = 0,                 -- 断点序号（该视频第几个暂停点，从 1 起；0 = 非断点）
    timeSec    = 0,                 -- 精确时间（秒）
  },
}
```

**规则**：
- `mediaPos` 只在剧情视频（S1~S9）播放/暂停时写入；循环背景（粒子、章节卡）不写。
- `flags` 是跨段落的临时状态，**有明确所有者和重置时机**（见 §8 状态所有权表）。
- `schemaVersion` 变更时提供迁移函数；加载时逐字段类型检查 + 默认值兜底（沿用《12》§4 原则）。

## 5. 视频断点交互时间表（13 段，S6 接入依据）

案例①："断点是媒体剪辑和游戏状态之间的契约，时间点需要在真实设备上反复校正。"

| 视频 | 时长 | 断点 | 交互类型 | 成功去向 | 失败/超时 | 恢复类型 |
|------|------|------|----------|----------|-----------|----------|
| S1 开场 | 30~45s | 播完 | 无（自动） | P02 探索 | 重试 S1 | 剧情（存位置） |
| S2 离别 | 40~60s | 播完 | 无（字幕+口型） | P05 讲述 | 重试 S2 | 剧情 |
| S3 守望 | 30~45s | 播完 | 无 | P06 讲述 | 重试 S3 | 剧情 |
| S4 落花 | 30s | 播完 | 无 | P07 接任务 | 重试 S4 | 剧情 |
| S5 无面鬼 | 45~60s | 结尾暂停 | 三选一（递水/陪坐/唤名，信念+1） | P23 互动反馈 | 三选必选一，无失败 | 剧情 |
| S6-1~5 记忆 | 15~20s/段 | 播完暂停 | 解读三选（信念+1） | 下一印证段 | 三选必选一，无失败 | 剧情 |
| S7 重逢 | 45~60s | 播完 | 无（结局演出） | 制作名单 | 重试 S7 | 剧情 |
| S8 放手 | 30~45s | 播完 | 无（结局演出） | 制作名单 | 重试 S8 | 剧情 |
| S9 传说 | 20~30s | 播完 | 无（结局演出） | 制作名单 | 重试 S9 | 剧情 |

**断点标注规范**（每段视频生成并导入后立即标注，真机校正）：
- 标出：暂停时间点 / 交互类型 / 成功去向 / 失败去向 / 是否写 mediaPos。
- 断点时间以"暂停那一刻"为准，标注到秒；首帧前 0.5s 内不设断点（防闪帧）。
- S5 与 S6 系列的"三选必选一"交互不需要失败路径，但要定义**选项锁定**（选中后立即锁，防连点双加）。

## 6. 媒体恢复策略与资源管理（S6/S8/S9 依据）

### 6.1 两类视频，两套策略（案例②核心）

| 类别 | 判定标准 | 恢复策略 | 素女篇实例 |
|------|----------|----------|-----------|
| 剧情视频 | 要求连续观看、进度有意义 | **保存并恢复播放位置**（mediaPos）；恢复时 seek 确认后再显示 | S1~S9 |
| 循环背景 | 不要求进度连续 | 恢复失败可**销毁重建** | 桃花粒子、章节卡背景、环境光效 |

> 先定义产品目标（这段必须连续看完吗？），再选策略。素女篇全部剧情视频走"存位置恢复"，循环层走"重建"。

### 6.2 读档恢复三步状态机（案例①核心："可播放"≠"已到目标时间"）

```
读档 → ① 播放器就绪（解码器/纹理/首帧就绪事件齐了？）
     → ② seek 到 mediaPos.timeSec 并确认到达（回调/轮询时间戳对齐）
     → ③ 移除遮罩，显示画面
任一步超时 → 进入重试流程（最多 N 次）→ 仍失败 → 明确错误界面（重试按钮/回标题）
```

**禁止**：把"播放器已就绪"当成"播放位置已到位"；固定延迟不能替代状态判断。

### 6.3 预加载 ≠ 首帧就绪（案例②）

资源下载完成后还要经过：**下载完成 → 解码器就绪 → 纹理就绪 → 首帧就绪 → 音频源就绪**。
- 首批高优先级预加载：S1/S5/S6-1（开局即用）；后续视频在"进入该章节块时"再预加载。
- 限制动态并发（建议同时 ≤2 个视频实例，真机核对解码并发与内存预算）。
- 仅在下一段视频可无分支预测时预热（素女篇主线线性，符合条件；但移动端先核对预算再启用）。

### 6.4 资源释放是玩法的一部分（案例②）

- 剧情视频**播放结束即释放**（尤其 S6 系列 5 段连续播放，段间必须回收，防"无声/画面抢占"）。
- 离开视频场景时**显式销毁播放器**（防泄漏）；S9 打磨清单记录：目标设备上播放器数量与内存峰值。
- 结局视频播完 → 释放 → 制作名单（纯 UI/粒子）→ 标题。

## 7. 测试与验收清单（合并两案例，S9 打磨期执行）

| # | 检查项 | 来源 | 通过标准 |
|---|--------|------|----------|
| 1 | 段落可达性 | ② | 每个段落能从章节入口进入、有明确完成出口；故事图从起点可达每个结局，无孤立节点 |
| 2 | 选择锁定 / 信念门槛 / 重开章节 | ② | 选项连点不双加；结局门槛（传说≥3 等）判定正确；重开章节状态正确重置 |
| 3 | 连续视频无无声/重复/旧场景延迟 | ② | S6 系列 5 段连播无无声、无重复播放、无上一段延迟回调串台 |
| 4 | 读档不闪帧、断点不重复触发 | ① | 读档不闪现第 0 帧；恢复后断点不会再次弹交互 |
| 5 | 前后台/通知栏返回连续 | ① | 切后台→回前台、通知栏返回，画面从正确位置续播；背景类循环正常重建 |
| 6 | 播放器数量与内存回落 | ② | 退出带视频的玩法后，播放器数量归零、内存回落（目标设备记录峰值） |
| 7 | 每改一条链路做可重复回归 | ① | 读档/切后台/回前台三条测试路径每次改动后全跑一遍 |

> 排查媒体问题时：先描述用户看到的症状，再沿媒体时钟 / 交互状态 / 场景生命周期三条链路分别画时序，**每次只改一条链路**，用可重复测试确认。

## 8. 状态所有权表（谁拥有、何时重置）

| 状态 | 层级 | 所有者 | 重置时机 | 序列化 |
|------|------|--------|----------|--------|
| belief / blossoms / memories / journal | 跨存档 | PlayerData | 永不（新游戏才清） | ✅ 存档 |
| endingsSeen / playCount | 跨存档 | PlayerData | 永不 | ✅ 存档 |
| flags（喂水/陪坐/唤名、章节解锁） | 跨段落 | PlayerData.flags | 通关后保留至新游戏？→ **终局结算后清空**（回声数据另存） | ✅ 存档 |
| 当前选中对象/悬停热点 | 场景内 | 场景对象 | 段落退出即弃 | ❌ 不存 |
| mediaPos | 跨场景 | PlayerData.mediaPos | 剧情视频推进时覆盖写 | ✅ 存档 |
| 播放器实例/粒子系统 | 场景内 | 场景对象 | 段落退出显式销毁 | ❌ 不存 |

## 9. 给 TTM 的能力追问增补（并入《12》§6，开工第一件事）

原 5 问之外，新增媒体恢复相关 3 问（两案例共同印证：这些坑在制造里是真实存在的）：

1. 视频播放是否支持 **seek 到指定时间并暂停**？一个场景能否同时存在多个播放器（剧情视频 + 循环背景）？播放器实例数量有无上限？
2. 视频的 **解码器就绪 / 首帧就绪 / 播放完成 / 暂停** 是否有独立事件或回调？能否据此实现"先确认位置再显示"？
3. 应用 **切后台 / 回前台 / 通知栏** 的事件回调是什么？后台时视频是否自动暂停或释放？
